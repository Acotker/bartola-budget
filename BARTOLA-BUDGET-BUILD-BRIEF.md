# Bartola Budget — v1 Build Brief

**Read this whole document before writing code.** It defines what to build, the exact math behind the core feature, the screens, and the visual language. Section 4 (the engine) is the product — everything else is packaging around it. If anything here is ambiguous, ask rather than guess.

---

## 1. What we're building

Bartola Budget helps someone living off a **fixed, finite pool of money for a fixed period of time** answer one question every day: **"Can I afford this?"**

It replaces static monthly budgeting with a single rolling daily number — **Safe-to-Spend (S2S)** — that already accounts for every known future obligation, and that recalculates itself continuously as real spending happens.

The product is not primarily an expense tracker or a ledger. It's a **daily decision-making tool**. A user should open the app, see one number, and immediately know whether the thing they're about to buy is fine. Every design and engineering decision should defer to that.

### Target user (v1)

Graduate students who are not earning income and are living off a known sum for a known stretch of time — e.g. *"I have $100,000 and I'm in school until July 31, 2028."* Closed system: known start, known end, no paychecks. That constraint is what makes v1 tractable, and we are deliberately not generalizing beyond it yet.

### The insight

Most budgeting apps tell you what you *did* (backward-looking, judgmental). This one tells you what you *can do today* (forward-looking, permissive). Money already committed to rent, groceries, and planned trips is invisibly set aside; whatever's genuinely free becomes a daily allowance that accumulates when you underspend. Underspending is rewarded by simply having more tomorrow. Overspending is absorbed by a small, quiet reduction in the daily number going forward — never a scolding.

**Tone rule for all UI copy: informative, never punitive.** No red-alert shaming, no "you're over budget!" language. When things go wrong the app explains the new reality and offers a concrete next action.

## 2. Vocabulary (use these exact names in code, DB, and UI)

| Term | Definition |
|---|---|
| **Plan** | The container for a user's finances: total pool amount, start date, end date. One active Plan per user. Editable at any time. |
| **Runway** | The span from Plan start date to Plan end date — how long the money must last. |
| **S2S** (Safe-to-Spend) | The rolling daily allowance for unplanned/ad hoc spending. Accumulates day over day when underspent. This is the hero number. |
| **Program Spend** | A named bucket of money reserved out of the pool for a specific purpose. Either **recurring** (rent, groceries, a monthly "trips" fund) or **one-time** (a specific dated trip). |
| **Occurrence** | One instance of a recurring Program Spend (this month's rent, this week's groceries). Generated by the recurrence rule. |
| **Spend Entry** | A real, logged transaction. Always tagged either as S2S or to a specific Program Spend occurrence. |
| **Baseline** | The current daily S2S grant, output of the engine. |
| **Deficit state** | When the engine produces a negative or near-zero Baseline — the plan is not viable as configured. |

## 3. Core model — how money moves

1. User has a fixed pool over a fixed Runway.
2. User creates **Program Spends**. Recurring ones are projected across **every occurrence through the end of the Runway and reserved in full, upfront** — not incrementally period by period. Rent at $1,500/month with 12 months left reserves $18,000 immediately. This is deliberate: it makes the S2S number honest from day one rather than artificially high early and collapsing later.
3. Whatever remains after all reservations funds **S2S**, spread evenly across remaining days → the **Baseline**.
4. Each day, the Baseline is granted. Unspent S2S **rolls forward and accumulates**. It never expires or resets.
5. User reports spending as one of exactly two types:
   - **S2S spend** — deducts from the accumulated S2S balance.
   - **Program Spend** — deducts from that program's own bucket. **Does not touch S2S.**
6. **Underspending never triggers anything.** Surplus stays in whichever bucket earned it and remains spendable there.
7. **Overspending triggers a full forward recalculation** (Section 4). Past days and already-banked balances are never rewritten.

### Handling irregular spending (trips, events) — no new object needed

Both patterns are ordinary Program Spends:

- **Recurring discretionary bucket** — e.g. a monthly or per-semester "Trips" fund that replenishes on schedule, sized for spending you know will happen but can't yet itemize. Underspend rolls forward inside that bucket.
- **One-time dated Program Spend** — once a specific trip is known, create it with its own date and amount. It reserves immediately and the S2S Baseline visibly drops, so the user sees the cost of that decision *today* and can shrink, re-date, or delete it on the spot.

This pairing is the heart of the user's mental model: pre-budget loosely, then convert to specifics as life firms up. A skilled user moves money between the two shapes fluidly.

## 4. The recalculation engine — exact specification

**This must be implemented as a pure, isolated, unit-tested module.** No engine math inline in UI components or route handlers. Given a Plan, its Program Spends, and all Spend Entries, it returns the current Baseline and all bucket balances. It should be deterministic and side-effect free, so the worked examples in Section 5 can be run directly as tests.

### Definitions

| Symbol | Meaning |
|---|---|
| `P` | Plan pool amount **+** all logged additional inflows (income, loans, gifts) |
| `A` | Sum of **all actual Spend Entries logged to date**, across every bucket, all time |
| `ARP` | Available Remaining Pool = `P − A` (money that genuinely still exists) |
| `RC` | Remaining Committed = sum of planned amounts of **all future occurrences** of all active Program Spends, dated from the effective date through the Runway end |
| `B_prog` | Sum of positive carried surpluses sitting in Program Spend buckets from **past** occurrences |
| `B_s2s` | Accumulated S2S balance **if positive**; `0` if negative |
| `UR` | Unallocated Remainder = `ARP − RC − B_prog − B_s2s` |
| `RD` | Remaining Days, from the effective date through the Runway end date, inclusive |
| **Baseline** | `UR / RD` |

Each day: `available S2S = carried balance + Baseline − today's S2S spend`.

### Two rules that make this consistent — do not skip these

1. **Preserved balances must be subtracted out of `UR`.** Banked S2S (`B_s2s`) and Program Spend surpluses (`B_prog`) are still sitting in `ARP` as unspent money. If they aren't subtracted, they get redistributed into the daily Baseline *while also* remaining spendable in their bucket — the user could spend the same dollar twice. This is the single most common way to get this engine wrong.

2. **A negative S2S balance is absorbed, not carried.** When accumulated S2S goes negative, set `B_s2s = 0`, run the recalc, and **reset the accumulated balance to 0** going forward. The overspend is already reflected in `A`, so it flows automatically into a slightly lower Baseline spread across all remaining days. Carrying the negative *and* lowering the Baseline would double-punish.

Together these give the desired asymmetry: **surpluses are protected, deficits are quietly smoothed forward.**

### Effective date convention

**A recalculation takes effect for tomorrow onward. Today's already-granted Baseline is never retroactively changed.** So `RD` runs from tomorrow through the Runway end, and the accumulated balance fed in is the balance *after* today's spending. This avoids re-granting a partially-spent day and is what makes the examples in Section 5 reconcile exactly.

### Recalculation triggers

Recalculate when:
- a Program Spend is created, edited, cancelled, or deleted
- the Plan is edited (pool amount, start date, or end date)
- additional inflow is logged
- **an overspend occurs** — an S2S entry exceeding the current accumulated balance, or a Program Spend entry exceeding that occurrence's remaining planned amount

Do **not** recalculate when:
- S2S is underspent on a day (it just rolls forward)
- a Program Spend occurrence is underspent (surplus stays in the bucket)

### Deficit handling

Baseline may go to zero or negative. This is a **friendly deficit state**, not a blocked or error state — the user is never prevented from logging real spending that really happened. Surface a clear, calm explanation that the plan isn't viable as configured, with concrete CTAs: edit or remove a Program Spend, extend the end date, add income, or reconcile the pool.

For v1, deficits are spread **evenly** across all remaining days. We expect to revisit this later (possibly front-loading short-term and easing long-term), but **ship the simple even split** — do not invent smoothing curves.

## 5. Worked examples — use these as the engine's unit tests

All figures verified. Unrounded values shown where precision matters; the engine should compute in integer cents and round only for display.

### Setup — "Maria"

| | |
|---|---|
| Pool | $60,000 |
| Runway | Sep 1, 2026 → Aug 31, 2027 = **365 days** |
| Rent | $1,500/month, 1st of month → 12 occurrences = **$18,000** |
| Groceries | $150/week → 52 occurrences = **$7,800** |
| Trips fund | $300/month, 1st of month → 12 occurrences = **$3,600** |

Total reserved = **$29,400** → `UR` = 60,000 − 29,400 = **$30,600**
**Baseline = 30,600 / 365 = $83.84/day** (83.8356)

#### Example 1 — Onboarding, before any Program Spends
`UR` = $60,000, `RD` = 365 → Baseline = **$164.38/day**. All of the pool funds S2S until Program Spends are added. Adding rent, then groceries, then the trips fund walks it down to $115.07 → $93.70 → **$83.84**. Each addition triggers a recalc.

#### Example 2 — A normal day: rollover, no recalc
Sep 1. Rent occurrence $1,500 paid exactly as planned. Groceries week 1 budgeted $150, user spends $120. Coffee $6 logged to S2S.
- Nothing is overspent → **no recalculation**.
- S2S end of day: 83.84 − 6 = **$77.84 carried**.
- Groceries bucket keeps a **$30 surplus**, still spendable on groceries.
- Sep 2 available S2S = 77.84 + 83.84 = **$161.68**.

#### Example 3 — S2S overspend triggers a recalc
State on **Sep 10, 2026**, before the purchase:
- S2S granted Sep 1–10 = 10 × 83.8356 = $838.36; S2S spent so far = $438.36 → **accumulated balance $400.00**
- Actual spend to date `A` = rent 1,500 + groceries 270 + S2S 438.36 = **$2,208.36**
- Past-occurrence surpluses: groceries (2 occurrences, $300 allocated, $270 spent) = $30; trips (Sep occurrence, $300 allocated, $0 spent) = $300 → **`B_prog` = $330**

User books a **$900 flight, logged to S2S**. Balance → **−$500.00** → overspend → recalculate for Sep 11 onward.

```
A    = 2,208.36 + 900          = 3,108.36
ARP  = 60,000 − 3,108.36       = 56,891.64
RC   = rent 11×1,500 = 16,500
     + groceries 50×150 = 7,500
     + trips 11×300 = 3,300     = 27,300
B_prog                          =    330
B_s2s (negative → absorbed)     =      0
UR   = 56,891.64 − 27,300 − 330 = 29,261.64
RD   = Sep 11 → Aug 31          =    355
Baseline = 29,261.64 / 355      = $82.43/day
```
S2S accumulated balance resets to **$0** for Sep 11.

**Consistency check the engine must also pass:** run the identical calculation *without* the flight and it returns exactly **$83.8356** — the original Baseline, unchanged. And the drop is precisely the deficit spread evenly: `500 / 355 = $1.41/day`, and `83.8356 − 1.4085 = 82.4271`. ✔ If your implementation doesn't reproduce both of these to the cent, the double-counting rules in Section 4 have been violated.

#### Example 4 — Program Spend overspend
Sep 15, groceries occurrence budgeted $150, user spends **$210** (over by $60). Assume S2S was spent exactly at Baseline Sep 11–15 (balance $0).
- The $60 overage is captured in `A`; the occurrence closes at its actual amount; future grocery occurrences are unchanged.
- `RD` = Sep 16 → Aug 31 = 350 → impact = 60 / 350 = $0.17/day.
- **Baseline: $82.43 → $82.26.**

Note the overage is **absorbed by the forward Baseline, not deducted from banked S2S.** Banked S2S is untouchable.

#### Example 5 — Planning a specific trip (the key product moment)
Sep 16, user creates a one-time Program Spend: *"Thanksgiving trip, Nov 25, $800."*
- `RD` = Sep 17 → Aug 31 = 349 → impact = 800 / 349 = $2.29/day.
- **Baseline: $82.26 → $79.96.**

The UI must show this delta explicitly on save — *"Your daily goes from $82.26 to $79.96."* That instant feedback is the product's differentiator: it prices a future decision in today's terms, and the user can immediately shrink, re-date, or delete it.

#### Example 6 — Deficit state
Same moment, user instead creates a **$30,000** trip. `UR` = 27,907.25 − 30,000 = −$2,092.75 → **Baseline = −$6.00/day.**

Show the friendly deficit state: explain the plan isn't viable as configured, offer CTAs (reduce/remove this trip, trim another Program Spend, extend the end date, add income). Do not block the action, do not scold.

#### Example 7 — Spending a Program Spend surplus
Trips fund carries a $300 September surplus; Oct 1 grants another $300 → bucket holds **$600**. User spends $550 on an October weekend → within budget → **no recalculation**, $50 surplus remains in the bucket. Surplus must be clearly visible in the UI as available-to-spend.

## 6. Epics — v1 scope

### Epic 0 — Account & auth
Standard email/password (or equivalent). Full data isolation per user: own Plan, Program Spends, S2S, history. No shared or social accounts in v1.

### Epic 1 — Onboarding
Minimal, three inputs: **total pool amount**, **start date** (defaults to today, editable, may be in the future for someone planning ahead), **end date**. On submit, create the Plan, compute Runway length and initial Baseline, and land the user on Home showing their first S2S number. Do **not** require Program Spend setup during onboarding — prompt for it afterward.

### Epic 2 — Plan management
Edit pool amount, start date, end date at any time. Log additional inflows (extra income, loan, gift) that increase the pool. Any change triggers a recalculation, and the resulting Baseline delta should be shown.

### Epic 3 — Program Spend management
Create, edit, cancel/delete. Each has a name (free text, optional), an amount per occurrence, and either a **recurrence rule** (weekly / bi-weekly / monthly, with an anchor day, projected through Runway end) or a **single target date** (one-time). Any change triggers recalculation with a visible Baseline delta. Each Program Spend shows: total reserved, spent to date, current bucket balance including surplus, and upcoming occurrences.

**No fixed category taxonomy.** Names are free text, never de-duplicated, never picked from a required list. Two buckets both called "Trip" are two independent buckets. Optional icon/emoji picker is fine as decoration only.

### Epic 4 — The S2S engine
Maintains accumulated balance per user. Runs the daily rollover at a fixed boundary in **America/New_York (Boston) time** — hardcoded for v1, no per-user timezone setting. Runs the recalculation on every qualifying trigger. Exposes the current Baseline and the deficit state.

### Epic 5 — Spend logging
The core daily interaction. User enters an amount, chooses **S2S** or a **specific Program Spend**, optionally adds a note, saves. Manual entry only — no bank feeds, no email parsing, no receipt photos. Updates the relevant bucket immediately; recalculates only on overspend. Must be fast: **logging a spend should take under five seconds and no more than three taps.** Optimize this flow harder than any other screen.

## 7. Screens

Mobile-first web app. Design for a phone viewport; it should remain usable on desktop but phone is the primary target.

1. **Auth** — sign up / log in. Minimal.
2. **Onboarding** — pool → start date → end date → confirmation revealing the first daily number. Make the reveal feel like a payoff; it's the first time the product's value lands.
3. **Home / Today** ⭐ *the hero screen* — the S2S number, enormous, dominating the viewport. Below it: today's date, a persistent **Log Spend** button, a compact strip of upcoming Program Spend occurrences, and days remaining in the Runway. Deficit banner replaces the number's normal treatment when applicable. Nothing else competes for attention here.
4. **Log Spend** — amount keypad → S2S or Program Spend toggle → (if Program) pick which → optional note → save → brief confirmation showing the updated S2S. The S2S/Program choice is the most important control in the app: make it unmissable and explain the difference in a single line of microcopy.
5. **Program Spends list** — one card per program showing reserved / spent / remaining and the next occurrence date. Surplus should read as *available*, not as leftover. Plus button to add.
6. **Add / Edit Program Spend** — recurring vs one-time toggle, amount, recurrence rule, dates. On save, show the Baseline delta prominently before returning.
7. **Program Spend detail** — occurrence history, bucket balance, edit/cancel/delete.
8. **Plan settings** — pool, start, end, log additional income, plus a summary: total reserved, total unallocated, days remaining.
9. **Activity / History** — chronological Spend Entries, filterable by bucket. Read-only in v1 apart from edit/delete of an individual entry (for correcting mistakes).
10. **Deficit state** — modal or takeover: plain-language explanation plus the CTA set from Section 4.

Target WCAG AA throughout.

The S2S number should animate when it changes — a brief count transition, not an instant swap. That motion is the product's signature: it makes the money feel alive and responsive rather than static. Keep everything else calm and fast.

## 9. Engineering guardrails

The stack is your call — pick something conventional, productive, and coherent, and commit to it. Constraints:

- **Money as integer cents.** No floats anywhere in storage or the engine. Round only at the display layer.
- **The engine is a pure, isolated module** with unit tests. Section 5's examples are the test suite — including the two consistency checks in Example 3. Get those green before building any UI.
- **Dates go through a real date library**, pinned to `America/New_York`. Recurrence projection across month boundaries, month-end anchors, and DST is where this class of app breaks.
- **Occurrences are derived from the recurrence rule**, not hand-materialized rows you have to keep in sync — unless you have a clear reason and handle drift.
- **Seed a demo user** matching the "Maria" scenario so the app can be explored immediately without manual setup.
- Mobile-first responsive. Real persistence and real auth — not mocked.

### Suggested data model (guidance, not gospel)

- **User** — id, email, credentials
- **Plan** — id, user_id, pool_amount_cents, start_date, end_date, timestamps
- **PlanAdjustment** — id, plan_id, type (income_add / pool_edit / date_edit), amount_cents, old_value, new_value, date, note
- **ProgramSpend** — id, plan_id, name, is_recurring, recurrence_rule, amount_per_occurrence_cents, start_date, end_date, target_date, status (active / completed / cancelled)
- **SpendEntry** — id, plan_id, date, amount_cents, type (s2s / program), program_spend_id, occurrence_ref, note, timestamps
- **S2SDailyLedger** (derived or stored) — date, baseline_cents, balance_start_cents, spend_cents, balance_end_cents

### Build order — do not build all epics at once

1. **The engine + its tests.** Nothing else until Section 5 passes to the cent.
2. **Thin end-to-end slice:** auth → onboarding → create one Program Spend → log one spend → see S2S update. Stop and confirm the loop works.
3. Full Program Spend management (recurrence rules, edit/delete, buckets and surpluses).
4. Home screen polish, Baseline-delta feedback, deficit state.
5. History, plan settings, additional inflows.

## 11. Locked decisions — do not re-litigate

- Recurring Program Spends reserve their **full projected total through the Runway end, upfront**.
- **Overspend triggers a forward-only recalculation; underspend never does.**
- Preserved balances (banked S2S, Program Spend surpluses) are **subtracted from `UR`**; negative S2S balances are **absorbed and reset to zero**.
- Recalculations take effect **tomorrow onward**; today's grant is never rewritten.
- S2S may go negative or to zero — a **friendly deficit signal with CTAs**, never a blocked state.
- **No category taxonomy.** Free-text names, independent buckets.
- **No preview/dry-run mode** in v1.
- Timezone hardcoded to **America/New_York**.
- Pool amount, start date, and end date are all **editable post-onboarding**; inflows can be logged anytime.
- History is **never rewritten** except by explicit user correction.
